# Model router v2: Jev-first task assessment

**Proposal for review.** Build a new routing engine alongside v1; keep the existing router in control until comparison shows a gain. Use TypeSafe Jev to assess what a task needs, not to choose or bill a route. Start with fresh Superagent tickets. Keep the current dashboard, history, and explicit model selection. No live inference or release is part of this proposal.

```text
Explicit model choice ──────────────────────────► existing pin path (skip Jev)
New unpinned task ─► bounded Jev assessment ─┐
                         local fallback ──────┤
Harness registry ───► allowed route catalog ───┼─► filter, rank, reserve ─► route + effort
Subscriptions ──────► account/window health ──┤                               │
Artificial Analysis ─► benchmark priors ───────┘                     measure outcome
```

## One decision per new task

1. **Describe the task once.** Use a pinned Jev version through [TypeSafe System One](https://docs.typesafe.ai/api/system-one.md) or its [OpenRouter Decisions equivalent](https://openrouter.ai/docs/guides/community/jev.md), not the managed Jev Router. In one request, ask bounded questions about difficulty, task family, visual inspection, tool needs, and insufficient information. Use a short approved task description and structured attachment flags, not transcripts, tool results, image bytes, account details, or a catalog dump. Do not retain the sent text in routing telemetry. Opt in to the external disclosure, set a request budget and a hard deadline, and don't retry in the foreground. For low confidence, timeout, or invalid output, use v1's local assessment. Do not let Jev relax known input requirements or grant tools. If the request needs a missing screenshot, flag missing input instead of treating model selection as the remedy.
2. **Filter before ranking.** Consider exact, allowed `(provider, model, effort)` variants only. Known modality, context including projected output, tool compatibility, current provider health, and billing policy come from the host or explicit route settings. Unknown required capability is not a match. If a user pins a route, use the existing validation and precedence rather than silently substituting. If no automatic route passes, return a reason; keep the current route only if it is policy-eligible, otherwise ask or defer rather than silently spending.
3. **Rank with separate budgets.** Compare expected task success and time using task-relevant public priors (where licensed) and local observations. Within quality and latency goals, prefer sustainable included quota when the strategy calls for it. Penalize pressure on the tightest applicable subscription window; never pool percentages from different accounts or windows. Compare metered cash separately. Optional provider credits are not included quota. Use an explicitly allowed cash or credit fallback only within its own limit. Recheck live eligibility and any local reservation together at admission. Provider percentages are observations, not a reservation or a provider-side guarantee, especially across processes or other apps.
4. **Keep the route stable.** Save a bounded decision ID and reason codes (classifier, capability, price/benchmark provenance, quota freshness and fallback). Tool continuations stay on the chosen route. Measure classifier and execution cash separately, chargeable attempts when observable, task acceptance, retries, latency, and included-quota consumption separately from cash and credits. Track estimated vs provider-reported numbers explicitly. A successful transport is not a successful task. Preserve v1's history and leave imported data tagged with its original meaning.

## The first integration must happen before model capture

The installed Harness loop claims messages synchronously, then immediately captures `agent.model.current()` (`dsh-agent-loop/src/agent.ts`, lines 293–303). Awaiting Jev inside the existing claim listener cannot route that step. The later request hook prohibits changing provider, model or effort.

**Start at Superagent's existing awaited launch path**, after checking the original request for a pin and before enqueueing the first assignment. Ask for a bounded advisory assessment of the original task, not the generated relay. For a live pilot, validate and reserve against the latest snapshots immediately before queueing; do not queue an assignment with no eligible route. Bind the decision to the assignment and message ID; release unused reservations on cancellation, expiry, duplicate delivery or failed admission. If a queued route can become ineligible before execution, require an admission check that can stop dispatch (or exclude that route from the pilot). The claim notification alone cannot block dispatch. A shadow decision must never set `modelPinned` or change a live request; a live auto-decision is also distinct from an explicit human pin. Only one engine owns selection and reservations in a live run. For general Harness input, keep v1 until the host has a supported awaited seam before model capture. Immediate claims can beat insertion-time precompute. Never change a running session after a late answer.

## Relative to the installed v1

| Dimension | v1 today | Proposed v2 |
| --- | --- | --- |
| Task needs | Local keywords, length, attachment count; one difficulty score | Jev evaluates difficulty and independent task needs; bounded local fallback. May reduce misroutes, but adds uncertainty, privacy review and paid network time. |
| Available routes | Hand-configured route list and startup validation | Same registry as the picker, refreshed without paid probes. Less curation, more metadata/permission checks. |
| Quota | Configured token/request weights, fixed windows and process-local reservations | Observed account/model windows where binding is known; local reservations and pressure remain estimates. Stronger signals, not a global spending lock. |
| Quality, speed and cost | Configured capability/speed and rates; actual usage and optional ratings in reports | Task-specific priors and local acceptance/latency/usage by route and effort. More evidence, but sparse, biased, and variant-dependent. |
| Failure and latency | No classifier network call; easy to reproduce locally | Bounded call plus deterministic fallback. Background refresh failures do not stall routing. More integration and operational complexity. |

## Evaluation and rollout

- **Offline first.** Freeze a held-out set (start with roughly 300 labeled, synthetic or explicitly approved redacted tasks), including short but difficult tasks, long but routine tasks, vision and text-only tasks, missing inputs, ambiguous or multilingual requests, and quota/health cases. Replay (A) current v1, (B) v2 with the same snapshots and local classifier, (C) v2 plus Jev, and (D) C plus licensed benchmark priors. Add a quota-only ablation if needed. This isolates which changes help; classifier accuracy alone cannot establish task success or savings.
- **Verify invariants before live use.** Test pins, missing/stale inputs, revoked routes, marketplace alias mismatches, concurrent reservations, quota exhaustion, credits disabled, refresh races, late results and cancellations. A replay must show no policy violations. Shadow later only with explicit approval and cap; count classifier price, abstentions, timeouts, and added p95 time to first model start. Example initial targets: 300 ms hard deadline and ≤250 ms p95 added admission delay, to be tuned from evidence.
- **Paired canary before replacement.** With approved limits, evaluate the same representative tasks by tests or blind review. Compare cash per accepted task including classifier and retries, quota per accepted task by account/window, success/rework and p95 end-to-end latency. Proposed go/no-go: at least 10% lower cash per accepted task without losing more than two percentage points of acceptance, or materially higher acceptance without spending more; no material quota or latency regression and zero policy violations. Use paired uncertainty intervals; if they cannot support the claim, keep v1. Roll back through a switch, not a data migration; prevent both engines from counting the same execution.

**Recommendation:** Approve the design and implement offline replay first. Build the bounded Superagent integration and ask for a supported subscriptions interface only if Jev and the additional data produce measurable value. General chat and automatic cutover are not part of that first implementation.
